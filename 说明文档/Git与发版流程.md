# Git 与发版流程

## 1. 仓库

- 位置：开发主目录本身，`.git` 在 `通道生效签名短链程序_开发主目录/.git`。
- 当前主分支：`master`。
- 纳入版本管理：源码、测试、文档、打包脚本、NSIS 脚本、模板、地区库、初始通道映射、AntdUI。
- 不纳入版本管理：`便携Python运行环境/`、`构建依赖/`、`构建临时目录/`、`输出/`、`测试临时目录/`、`历史备份/`、`.venv*/`、`__pycache__/`、`发布资源/*移动/`、`源码/通道生效签名短链工具/*移动/`。
- `.gitattributes` 关闭换行转换，模板、图标、DLL 按二进制保存，避免不同电脑拉取后字节变化。

## 2. 日常提交

```powershell
git status
git diff
git add -A
git commit -m "fix: 说明改了什么"
```

提交信息建议使用以下前缀：

| 前缀 | 用途 |
|---|---|
| `feat:` | 新增功能或业务规则 |
| `fix:` | 修复缺陷 |
| `build:` | 打包、版本号、构建脚本 |
| `docs:` | 文档 |
| `test:` | 测试 |
| `chore:` | 维护、清理 |

不要使用 `git add -f` 强行加入已忽略目录；不要把真实运营商样例或客户数据提交到仓库。

## 3. 发版步骤

1. 完成代码修改，运行 `运行测试.ps1`，确认全部通过。
2. 更新 `版本.json`：
   - `productVersion` 按第 4 节规则提升；
   - `releaseDate` 填本次发版日期。
3. 更新 `版本说明.md` 顶部发版记录和 `用户使用说明.md` 的适用版本。
4. 提交所有修改：
   ```powershell
   git add -A
   git commit -m "release: 1.4.0"
   ```
5. 确认工作区干净：`git status` 不应有未提交文件。
6. 构建：
   ```powershell
   powershell -ExecutionPolicy Bypass -File .\生成安装包.ps1
   ```
   同版本同日期覆盖时加 `-Force`。
7. 核对 `输出\构建结果.txt`：
   - Git 提交应为当前提交；
   - 不应出现“（含未提交修改）”；
   - 测试状态为“全部通过”；
   - 记录安装包 SHA-256。
8. 建议打标签：
   ```powershell
   git tag -a v1.4.0 -m "通道生效签名短链程序 1.4.0"
   ```
9. 分发 `输出\通道生效签名短链程序_安装版_<版本>_<日期>.exe`。不要分发 `构建临时目录`。

如果构建后还需要改代码，改完必须重新测试、提交并重新构建；不要用旧安装包代替新提交。

## 4. 版本号规则

`productVersion` 采用 `主版本.次版本.修订号`：

- **修订号**：修复缺陷、文案、打包流程调整，不改变业务规则。
- **次版本**：新增功能或调整业务规则，向下兼容。
- **主版本**：数据结构、导入流程或使用方式发生不兼容变化。

`releaseDate` 使用发版当日日期。运行环境版本和主码号映射种子由构建脚本按内容哈希生成，不需要手工维护。

## 5. 回滚

- 代码回滚优先使用 `git revert <commit>`，保留历史。
- 临时查看旧版本：`git switch --detach <tag>`，看完切回 `master`。
- 发布回滚：检出上一个 tag，重新执行 `生成安装包.ps1` 生成旧版本安装包；不要手工替换安装包内的文件。
- 用户电脑的运行环境按版本号隔离在 `%TEMP%\通道生效签名短链程序运行环境\<运行环境版本>`，回滚后会使用旧版本自己的缓存目录，不会和新版本混用。
- 主码号资料保存在 `%LOCALAPPDATA%\通道生效签名短链程序`，回滚程序不会删除或覆盖用户资料；映射种子变化时程序会先备份再更新。

## 6. 常用检查

```powershell
git log --oneline --decorate -10
git status --short
git diff --stat
git tag --list
```

构建结果和安装包都在 `输出/`，已被 Git 忽略；需要归档时单独保存安装包和 `构建结果.txt`。
